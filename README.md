# Creeper Industry

`Creeper Industry` 是一个基于 **NeoForge 1.21.1** 的 Minecraft 模组，核心主题是“苦力怕、爆炸、信号工程与危险工业化”。

项目当前已经有可运行原型，重点不在传统的“发电 -> 输电 -> 用电”，而在一套以“信号”为核心媒介的工业系统：

- 爆炸事件可以直接产生脉冲信号
- 机器可以产生连续信号
- 信号会在空气、方块和导管中传播、衰减、聚合
- 机器读取的是目标位置上的最终聚合结果

## 当前重点系统

### 信号系统

当前仓库里已经实现了信号系统的基础规则与正式运行时骨架：

- 爆炸脉冲信号
- 连续信号源与更新链
- 接收端刷新与局部重算
- 检测器调试显示
- 导管网络接入传播计算
- 按服务器维度隔离的 `SignalRuntime`
- 脉冲、连续源与拓扑变化共用的集中刷新队列
- 维度卸载和服务器停止时的统一运行时清理

信号的关键概念：

- 幅值：信号强度
- 周期：离散 tick 周期
- 波形：当前为方波
- 相位：决定当前 tick 采样结果

### 信号运行时

信号源类型声明与世界运行状态已经分离：

- `CISignalSourceTypes` 只声明全局只读的信号源类型。
- 每个 `ServerLevel` 通过非持久化 Level Attachment 拥有独立的 `SignalRuntime`。
- 信号源仓库、接收端索引、导管缓存、聚合缓存和刷新队列不会跨维度或跨存档共享。
- 接收端在方块实体加载时注册，在拆除或区块卸载时注销。
- 同一 tick 内批量加载的接收端只触发一次连续信号活动目标重建，避免大型多方块放置时重复全量计算。
- 连续信号只刷新可能受影响的活动目标；生态瓶和检测器不再各自运行信号刷新 ticker。
- 同一 tick 内由脉冲、连续源变化和导管拓扑变化产生的目标会先合并去重，再统一结算。
- 运行时状态不写入存档；维度卸载或服务器停止时统一清理，并在下次加载时从世界状态重新建立。

### 导管系统

导管不是六面漏风的通用信号方块，而是“内部无损传输网络”：

- 信号在普通介质中按曼哈顿距离衰减
- 信号在导管网络内部无损传播
- 导管只能通过“接口”与外界交换信号
- 接口不是独立方块，而是安装在导管六个面的同格挂件

当前规则下：

- 没有接口的导管，不会和空气或普通方块直接连通信号
- 只有装了接口的那一面，才能作为导管的输入/输出面
- 接口增删会触发导管网络缓存刷新与相关接收端重算

## 当前连续信号规则

连续信号当前采用离散方波采样，只支持偶数周期：

- `2 tick`
- `4 tick`
- `6 tick`
- `8 tick`

采样规则统一为：

- 前半周期为 `+A`
- 后半周期为 `-A`

例子：

- `2 tick`: `+A, -A`
- `4 tick`: `+A, +A, -A, -A`
- `6 tick`: `+A, +A, +A, -A, -A, -A`

为了避免全偶数周期下所有信号天然锁相，连续信号源现在正式带有相位：

- 相位是 `0 ~ period-1` 的离散 tick 偏移
- 相位由机器位置和源 id 稳定生成
- 同一台机器在同一位置时，相位稳定
- 不同机器通常不会默认同相

这套规则的目的：

- 保持方波定义纯净，不再为奇数周期打补丁
- 让连续信号叠加真正受相位影响
- 避免等效值长期退化成单一锁相结果

## 检测器读数

`Signal Update Detector` 当前会显示三类值：

- `equivalent_value`：等效值，表示聚合结果的等效强度
- `instantaneous`：当前 tick 的瞬时值
- `last_non_zero`：最近一次非零等效值

其中：

- 纯连续信号时，等效值来自公共周期内叠加波形绝对值的平均
- 若当前 tick 混入脉冲信号，则该 tick 按瞬时叠加结果结算

## 生态瓶系统

三类生态瓶现在共用数据包可重载的 `biosphere_cultivation` 配方：

- 配方声明生态瓶类型、模板 `Ingredient`、可选消耗品、一个或多个产物以及信号要求
- 模板物品不会被消耗，消耗品数量与产物数量由配方声明
- 多产物配方可以通过潜行右键生态瓶切换当前产物
- 当前基础信号要求为幅值至少 `9` 且瞬时值为正，仍按信号上升沿结算一次
- 信号条件只由当前模板对应的配方决定；缺少消耗品只会阻止生产，不会把持续高信号误判为新的上升沿
- 配方位于 `data/creeper_industry/recipe/biosphere/`，数据重载后由 Recipe Manager 重新查询
- 生态瓶放置与拆除不使用客户端单格预测，统一等待服务器确认整座多方块结构，避免组成部分分批出现或消失

### Botanical Biosphere

当前已经实现 `Botanical Biosphere`（植物生态瓶）的第一版可用逻辑，供后续开发时参考：

- 方块本体当前实现为 `X=3, Y=7, Z=2` 的多方块结构，也就是水平占地 `3x2`、高度 `7`
- 右键任意一个组成方块，都会打开同一个控制面板
- 当前界面包含 `3` 个槽位：树苗槽、骨粉槽、产出槽
- 树苗现在作为“产物模板”使用，不会在每次生产时被消耗
- 骨粉作为实际消耗品，每次成功触发生产只消耗 `1` 个
- 产物通过数据配方由树苗模板映射为对应原木，当前已支持常见树苗、红树胚轴、杜鹃花与盛开的杜鹃花
- 正式模型资源位于 `src/main/resources/assets/creeper_industry/models/block/botanical_biosphere/`，当前由上/中/下三段源模型拆分为 `part_x*_y*_z*.json`

当前运作规则如下：

- 生态瓶接入现有信号系统，而不是使用炉子式“燃烧/进度条”逻辑
- 当生态瓶接收到一次导管传来的聚合信号，且该次信号满足“幅值 `> 8` 且当前瞬时值为正”时，会尝试生产
- 每次有效触发只产出 `1` 个对应原木
- 每次有效触发只消耗 `1` 个骨粉
- 同一波强信号只会在“由未触发进入触发”的那个边沿结算一次，避免持续高电平重复刷产物
- 同一游戏刻内如果多个组成块同时收到同一波信号，也只会实际结算一次产出

当前多方块与容器的实现约定：

- `3x2x7` 结构的每个组成方块都带有方块实体，用作信号接收代理和容器访问代理
- 实际库存仍集中在控制器方块（`x_part=0, y_part=0, z_part=0`）上
- 非控制器部分的菜单打开、物品访问、信号触发都会转发到控制器处理
- 这样做的目的是让导管接口和漏斗可以直接作用在结构的不同组成块上，而不需要额外的“外壳方块”逻辑

当前漏斗交互规则：

- 从生态瓶底部访问容器时，只暴露产出槽
- 因此底部漏斗只能抽走产出槽中的物品
- 输入槽（树苗、骨粉）不会被底部漏斗抽出
- 非底部方向默认只允许向输入槽插入，不允许抽走产出

当前界面状态：

- 已移除临时的“炉子燃烧”表现
- 当前界面是自定义绘制的三槽调试版 UI
- 后续如果要替换为正式美术资源，只需要继续调整 `BiosphereScreen`

### Monster Biosphere

- 使用怪物刷怪蛋作为不消耗的模板。
- 当前不需要额外消耗品。
- 产物覆盖原有怪物掉落表；存在多个候选产物时可通过潜行右键切换。
- 每次有效信号只产生 `1` 个当前选中掉落物。

### Zoological Biosphere

- 使用动物刷怪蛋作为不消耗的模板，并根据动物消耗对应饲料。
- 当前支持牛、猪、羊、鸡、兔和蜜蜂。
- 牛、羊、鸡和兔提供多个可选产物，可通过潜行右键切换。
- 动物与怪物生态瓶当前使用明确的占位方块模型，正式多方块美术资源后续单独接入。

### 多方块模型接入工作流

后续如果要把新的 Blockbench 模型接入成类似生态瓶这种多方块结构，建议固定按下面流程处理：

1. 先把原始模型 JSON 放进临时目录，例如 `modeltest/`，不要直接把这个目录当正式资源目录使用。
2. 检查每个源模型的包围范围、贴图引用、上中下分段关系，先判断它天然适合做成多大的宽度、深度和高度。
3. 如果模型天然朝向和设计文档的口头描述不一致，优先顺着模型天然坐标实现；只有在确实需要时，再额外做整体旋转。
4. 先改多方块代码中的尺寸定义，例如 `X_PART`、`Y_PART`、`Z_PART` 的范围，以及放置循环、结构遍历循环，确保代码尺寸和模型尺寸一致。
5. 给每段源模型加全局偏移，把下、中、上几段拼成一个完整的大模型；如果顶部模型存在负 `y`，必须先补上正确偏移再继续拆分。
6. 再把完整模型按 `16x16x16` 的方块网格切分，生成正式子模型到 `src/main/resources/assets/<modid>/models/block/<block_id>/part_x*_y*_z*.json`。
7. 正式资源目录通常至少包含 `base.json`、`empty.json`、`preview.json` 和所有 `part_x*_y*_z*.json`。
8. 同步重建 `blockstates/<block_id>.json`，把每个 `x_part/y_part/z_part` 组合映射到对应子模型；没有几何体的格子映射到 `empty`。
9. 保持常规入口结构：`models/block/<block_id>.json` 指向 `preview`，`models/item/<block_id>.json` 指向 block model。
10. 删除旧的正式子模型目录，避免旧文件残留导致新旧资源混用。
11. 最后至少做两轮验证：先验证所有 JSON 能正常解析，再用自己的 Gradle 环境执行 `build` 和 `runClient` 观察放置、碰撞、预览和贴图是否正确。

这套流程当前已经在 `Botanical Biosphere` 上实践过一次，正式资源目录位于 `src/main/resources/assets/creeper_industry/models/block/botanical_biosphere/`，可以直接作为后续类似内容的参考模板。

## 代码目录

```text
src/main/java/com/secondition/creeperindustry
├─ content
│  ├─ energy
│  │  ├─ signal
│  │  └─ transmission
│  ├─ logistics
│  └─ production
├─ foundation
└─ CreeperIndustry.java
```

重点目录：

- `content/energy/signal`：信号源、传播、聚合、刷新、接收与运行时服务
- `content/energy/signal/runtime`：按维度隔离的信号运行时、访问入口与生命周期事件
- `content/energy/transmission`：导管、接口与导管网络
- `docs/design_draft.md`：当前规则、约束与设计取舍
